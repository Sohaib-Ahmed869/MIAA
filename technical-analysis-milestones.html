System Architecture

The donation platform is built as an extension of the existing MIAA website — not a separate system. All new modules share the same React front end, the same backend API, the same hosting infrastructure, and the same admin CMS the MIAA team already uses. The additions are scoped to five new server-side modules, three new API integration layers, and a set of new front-end pages and components.

Layer Breakdown
Client Layer
React Front End
  • Donation widget (embeddable, CMS-controlled)
  • Homepage hero integration
  • Campaign & event pages
  • Checkout flow (ticket + optional donation upsell)
  • Donor account portal (login, history, manage subscriptions)
  • Admin CMS — new donation, campaign, and event sections
  • Fully mobile-responsive (all breakpoints)
Application Layer
Backend API (Node.js)
  • Donation Processing Module
  • Event Registration Module
  • Campaign & Appeal Module
  • Donor Account & Auth Module
  • Admin & Reporting Module
  • Webhook Handler (Stripe, PayPal)
  • Audit Logging Service
Data Layer
Database (existing infra)
  • Donors, Donations, Subscriptions
  • Campaigns, CampaignProducts
  • Events, EventRegistrations
  • InstallmentPlans, Payments
  • AuditLogs
  • PeerFundraisingPages
  • AdminUsers
Payment Layer
Stripe + PayPal
  • One-time charges
  • Subscription billing (recurring)
  • Saved payment methods
  • Apple Pay / Google Pay (Stripe)
  • Refunds and cancellations
  • Webhook event delivery to backend
  • PCI-compliant — card data never touches MIAA servers
Integration Layer
External Services
  • Brevo — donor & subscriber sync
  • Ticket Tailor — optional push for large events
  • Email (SMTP / Brevo transactional) — receipts and confirmations
  • MIAA CMS — content management for all donation widgets
Infrastructure
Hosting & Scaling
  • Existing MIAA hosting infrastructure
  • Auto-scaling — capacity adapts to concurrent users
  • HTTPS / TLS throughout
  • Staging environment mirrors production
  • Environment-based API key management
Single-system principle: No new hosting account, no new dashboard, no new platform to learn. Every feature described in this document is administered from the same MIAA CMS the team already operates. A dedicated donations-only portal is provided for team members whose role is exclusively donor management.

API Endpoints

All endpoints are RESTful JSON APIs served under the existing MIAA backend. Auth uses session tokens for the donor portal and admin-scoped JWT for the CMS.

Donations & Subscriptions
MethodPathDescriptionAuth
POST /api/donations/checkout Initiate a one-time or recurring donation. Returns a Stripe Payment Intent or PayPal Order. Optional (guest or donor)
POST /api/donations/webhooks/stripe Receive Stripe webhook events (payment_intent.succeeded, invoice.paid, subscription.deleted, etc.) Stripe signature
POST /api/donations/webhooks/paypal Receive PayPal IPN/webhook events. Confirms payment and updates donation status. PayPal signature
GET /api/donations/my Donor's donation history, receipts, and active subscriptions. Donor session
PUT /api/subscriptions/:id/cancel-request Donor requests cancellation. For committed installments, creates an admin approval task. Donor session
PUT /api/admin/subscriptions/:id/approve-cancel Admin approves or rejects a donor cancellation request. Admin JWT
Campaigns & Events
MethodPathDescriptionAuth
GET /api/campaigns List active campaigns (public). Includes total raised, goal, and linked event. Public
POST /api/admin/campaigns Create a new campaign. CMS action. Admin JWT
GET /api/events/:slug Fetch public event details including ticket price, capacity remaining, and registration form schema. Public
POST /api/events/:slug/register Register for an event. Processes ticket payment and optional donation upsell in a single transaction. Optional
GET /api/admin/events/:id/registrations Admin view of all registrations for an event including payment status. Admin JWT
Admin & Reporting
MethodPathDescriptionAuth
GET /api/admin/donations Paginated donation list with filters (date range, status, campaign, payment method). Admin JWT
GET /api/admin/donors/:id/tax-statement Generate a downloadable PDF annual tax statement for a specific donor. Admin JWT
GET /api/admin/audit-log Full audit log — paginated, filterable by user, action type, and date. Admin JWT
GET /api/admin/export/donations.csv Export donations to CSV for reconciliation or external reporting. Admin JWT

Third-Party Integrations

Stripe
Payment
  • Payment Intents API for one-time charges
  • Subscriptions API for recurring (weekly / monthly / annual)
  • Customer API — saved payment methods per donor
  • Stripe Elements embedded in checkout (PCI scope minimised)
  • Apple Pay & Google Pay via Payment Request Button
  • Webhook endpoint receives: payment_intent.succeeded, invoice.paid, customer.subscription.deleted
  • Test mode during development; live keys switched at go-live
PayPal
Payment
  • PayPal Orders API for one-time payments
  • Billing Agreements for recurring PayPal giving
  • PayPal JS SDK embedded in checkout alongside Stripe
  • Webhook receives: PAYMENT.CAPTURE.COMPLETED, BILLING.SUBSCRIPTION.CANCELLED
  • Sandbox environment during development and UAT
  • Live credentials activated 72 hours before go-live
Brevo (CRM)
CRM
  • Contacts API — upsert donor on first donation (dedup by email)
  • Transactional email API — donation receipts & event confirmations
  • Custom attribute tagging — donation frequency, campaign name, event name
  • Newsletter opt-in synced at registration
  • All API calls use MIAA's existing Brevo account and API key
Ticket Tailor
Ticketing
  • Optional push: registrations made on the MIAA website can be mirrored to Ticket Tailor
  • Uses Ticket Tailor API — creates an attendee record per registration
  • Triggered only when ticket_tailor_event_id is set on the event record
  • MIAA retains flexibility to use either platform for any given event
  • QR code scanning remains a Ticket Tailor function (not in scope)
Email (Transactional)
Email
  • Brevo transactional API used for all automated emails
  • Templates: donation receipt, event confirmation, cancellation request, admin alert
  • Admin notification on every completed donation
  • Annual tax statement delivered as PDF email attachment
  • All emails from MIAA-branded sender domain
MIAA CMS
Infra
  • All donation campaigns manageable without developer involvement
  • Hero slides — each slide's donation widget is independently controllable
  • Event pages — create, edit, and publish from the CMS
  • Donation product presets — admin sets amounts, causes, and homepage visibility
  • Dedicated donations-only portal for finance/donor-management team members

Environments & Development Workflow

Three environments run in parallel throughout the build. All payment gateways use test/sandbox credentials until production go-live on 25 July 2026.

Environment 01
Development
  • Local developer environments
  • Stripe test mode keys
  • PayPal sandbox credentials
  • Brevo test account
  • Feature branches per module
  • Unit tests run on every commit
Environment 02
Staging (UAT)
  • Hosted — mirrors production infrastructure
  • Stripe test mode (MIAA can do test payments)
  • PayPal sandbox (MIAA can test PayPal flow)
  • Full email sending enabled to MIAA test addresses
  • Accessible to MIAA team from Week 3 onward
  • All UAT feedback captured and tracked against this environment
Environment 03
Production
  • Live MIAA website
  • Stripe live mode keys (switched 24h before go-live)
  • PayPal live credentials
  • Brevo live account and sender domain
  • Go-live: 25 July 2026
  • Post-launch monitoring for 48 hours

Development Workflow

Branching Strategy

  • One feature branch per module (donation-core, event-registration, campaign, admin-portal, integrations)
  • Pull request review before merging to main
  • Staging auto-deploys from main
  • Production deploy is a manual tagged release

Testing Approach

  • Unit tests for all payment calculation logic
  • Integration tests for Stripe and PayPal webhook handlers
  • End-to-end test: complete donation checkout (Stripe test card)
  • End-to-end test: event registration + donation upsell
  • Mobile responsiveness verified across iPhone, Android, tablet

Risk Register

RiskLikelihoodImpactMitigation
Stripe live API keys not provided before Week 4 High High Requested from MIAA by end of Week 2. Think Studio can create a Stripe account under MIAA if needed and transfer ownership post-launch.
PayPal live credentials delayed Medium Medium PayPal can be omitted at go-live if credentials are not ready — Stripe covers Visa, Mastercard, Apple Pay, and Google Pay as a safe fallback.

Brevo transactional email goes to spam Low Medium SPF and DKIM authenticated on MIAA sender domain. Brevo warm-up required if the domain is new to transactional email — handled in Week 2.
Traffic spike on Gala Dinner night overwhelms server Low High Auto-scaling infrastructure adapts to concurrent users. Load testing performed in Week 4 to confirm capacity before go-live.
